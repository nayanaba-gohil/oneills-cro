## Integration steps

1. Add the brand tokens (`brand-*`, `navy-*`, `font-display`). Add the homepage template folder to Tailwind `content` so the classes compile. Rebuild CSS.
2. Load fonts: Inter 400/500/600/700 and Space Grotesk 500/700. These are the fonts the live site uses today (Inter for text, Space Grotesk for headings; checked 27 Oct 2026). The O'Neills logo lettering is an image, not a web font. Self-host them, or preload from Google Fonts.
3. Output `icons.html` once sitewide.
4. Copy `hyva/Magento_Cms/` into the child theme and empty the homepage CMS page content. The template outputs a `<div>`, not `<main id="maincontent">`, because Hyvä's page layout already renders that element. Every Alpine attribute uses CSP-safe syntax: only property names, getters and argument-free methods.
5. The template already includes the components (`js/oneills-home.js`, registered with `$hyvaCsp->registerInlineScript()`) and the JSON-LD.
6. Pass the tyre size combinations JSON into the `tyre_size_combinations` block argument (see Tyre and wheel finder).
7. Header and footer: port the structure from the reference files (details below).
8. Remove the old floating "Call now", "Text us" and back-to-top buttons. On mobile, the sticky bar in `footer.html` is the only floating element. If the Text us widget must stay, put it inside the sticky bar instead of floating over it.

## Head and SEO

- **Locale:** set Stores > Configuration > General > Locale to **English (Australia)** so `<html lang="en-AU">` is output. Today it is `lang="en"`.
- **Title:** `Tyres & Car Servicing Newcastle | O'Neills Tyre & Autocare`
- **Meta description:** `Family owned since 1961. Buy tyres online or book a service at 8 O'Neills stores across Newcastle, Lake Macquarie and the Hunter.`
- **Open Graph:** add `og:title`, `og:description`, `og:image` and `og:locale` = `en_AU` (values are in `index.html` `<head>`). The live homepage has none.
- **One H1:** "Tyres, wheels and car servicing across Newcastle and the Hunter". The slogan is now real text, not baked into the hero image. Every section has an H2, and the cards inside a section use H3. Don't use H4 to H6 in the footer: column titles are `<p>` inside a labelled `<nav>`.
- **No `aggregateRating` in schema.** Google treats review markup on your own Organization or LocalBusiness as self-serving, and doesn't allow ratings aggregated from Google into your own markup.
- Store data (address, phone, hours, Google place IDs) appears in 3 places: the store cards, `STORES` in the JS, and the JSON-LD. If anything changes, update all 3, plus the location pages and the Google Business Profiles.

## Components

### Tyre and wheel finder (`ohFinder`)
- **Tabs:** Buy Tyres and Buy Wheels, each searched by size or by vehicle. The panel has a fixed minimum height (`min-h-[25.25rem]`, the tallest view) and the column a fixed width, so switching tabs, modes or long vehicle names never resizes the hero. Every view has a hint bar of the same height (`min-h-[4.75rem]`) at every width: an outlined capsule plus one line of help. Tyres by size shows 205/55R16, wheels by size shows 5x114.3, and by vehicle shows a "Call us" pill as the fallback for a vehicle that isn't listed (below 1024px it opens the call sheet via `ohFinder.openCall`; on desktop it links to `#stores`).
- **Selects:** every finder select draws its own chevron (`#i-chevron-down`, 8px from the border) and uses `appearance-none bg-none`, which also removes the `@tailwindcss/forms` arrow. Keep `bg-none` if the classes are edited.
- **Different front and rear sizes:** the rear row has the same labels and order as the front. Rear profile unlocks after rear width, rear rim after rear profile. "Book a service" was removed from the hero; booking stays in the header, the services section and the mobile sticky bar.
- **Tyre sizes:** the live tyre size form renders `data-combinations` (6,389 rows of `{width_val, width_label, profile_val, profile_label, rim_val, rim_label}`). Output the same JSON on `#tyre-finder` (`tyre_size_combinations` in the layout). Profile and rim then only list sizes that exist for the chosen width. Without it, static lists are used.
- **Tyre search URL:** `/catalogsearch/result/?q=205/55R16&width=<id>&profile=<id>&rim_diameter=<id>`, as the live form does today. A staggered (different rear size) search adds `staggered=1`, `rear_width`, `rear_profile` and `rear_rim_diameter`. Map these to whatever the search module expects.
- **Wheel search URL:** `/catalogsearch/result/?q=wheels&diameter=&wheel_width=&pcd=&stud_pattern=&offset=`, the same params as the live wheel form. Stud pattern is worked out from the PCD (5x114.3 sends `5 Stud`), so the user picks one field instead of two.
- **Wheel options:** diameter, width, PCD and offset lists mirror the live form. The live PCD attribute has broken values without the "x" (4100, 5114.3, 6139.7 and more). Clean those up in the attribute options.
- **Wheels by vehicle:** submits to `/wheels/result`. That route needs confirming or building.
- **By vehicle:** calls `/tyres/api/vehicle?type=makes|years|models|series`, the same endpoint as the live `vehicleFinder()`. It then submits to `/tyres/result?make=&year=&model=&series=`. **Check these param names against the live component.**
- **API errors:** no error message is shown (client decision). If a call fails, that select just stays empty.

### How buying tyres online works (`ohSteps`, section 4)
- Brand blue (`bg-brand-600`), styled after the "If you've got wheels, you need O'Neills" poster: white text, amber step numbers, and a line-art convoy along the bottom (hatch, prime mover, 4WD wagon, van, dual-cab ute, box truck, sedan, tractor).
- **Desktop (1024px and up):** a tyre-print swirl stays pinned (`position: sticky`) in the left column while the 4 steps scroll past on the right. The step whose top has passed the middle of the screen is active: its number shows inside the print, the print turns 90 degrees per step, the step gets an amber left border, and the convoy rolls 48px forward. This is worked out on scroll and resize (once per frame), so jumps and reloads mid-page are handled.
- **Phones and tablets:** no pinning; each step has its own small tyre print with its number.
- All 4 steps are plain HTML in an `<ol>`; only the visual state depends on JS. Transitions are off for `prefers-reduced-motion`. The convoy only moves when the visitor scrolls, never on its own (WCAG 2.2.2).
- **Sticky needs no `overflow: hidden`** on the section or any ancestor (same as the header). Check `.page-wrapper` in the theme.
- Graphics: `g-tread-swirl` (viewBox 200 x 200) and `g-convoy` (730 x 54, tiles seamlessly) both use `currentColor`. Change them in `tools/graphics.py`, then run `python3 tools/graphics.py` to rewrite them in `src/icons.html`.

### Google reviews (`ohReviews`, section 6)
- **Row 1:** heading and subtext on the left; on the right, the overall Google summary (logo, 4.7, stars, 2,155 reviews across 8 stores) with "From each store's Google Business Profile, October 2026" under it.
- **Row 2:** one capsule per store (name and rating), most reviewed first; Broadmeadow is selected by default. ARIA `tablist`; left and right arrow keys move between stores. On phones the row scrolls sideways.
- **Row 3:** up to 3 review cards for the selected store (stars, text clamped to 4 lines, reviewer photo or initial, name, store, date, Google mark), then two buttons for that store: "Read all N reviews" (`search.google.com/local/reviews?placeid=`) and "Write a review" (`search.google.com/local/writereview?placeid=`). Both open Google in a new tab.
- **Review cards need a real feed. Never hard-code or write reviews.** Either render the cached reviews into the page as `<script type="application/json" id="...">` and set `data-json` on the section to that id (best: no extra request), or set `data-endpoint` to a JSON URL. Same shape either way, keyed by store: `{"broadmeadow": [{"id", "author", "authorUrl", "photo", "rating", "text", "when"}], "beresfield": [...], ...}`. Keys: broadmeadow, beresfield, gateshead, warnersBay, belmont, morisset, kurriKurri, cessnock. Source: Google Places API (New), Place Details with `reviews` (up to 5 per place: `authorAttribution.displayName`, `.uri`, `.photoUri`, `rating`, `text.text`, `relativePublishTimeDescription`), cached server-side and refreshed daily. Keep the author name, photo and link (Google requires the attribution). With no endpoint, or no reviews for a store, the cards stay hidden and only the two Google buttons show.
- **Preview only:** `index.html` inlines `data/preview-reviews.json` (clearly labelled sample cards for layout review) through `data-json`, so the cards show even when the file is opened straight from the folder. `tools/build.py` adds that only to the preview; the Hyvä template has no sample data. Never deploy the sample file.
- **Keeping ratings current:** update the per-store ratings and counts in `tools/lower_sections.py` monthly, or render them from the Places API (`rating`, `userRatingCount`).
- **Remove the Trustpilot badge.** The brand has no Trustpilot profile.
- **Don't use the Birdeye page (`reviews.birdeye.com/o-neills-tyres-167590212838801`).** It belongs to O'Neills Tyres, 61 Melbourne St, East Maitland, a different business that isn't one of the 8 stores.

## Performance and accessibility

- **Hero image:** the hero photo is the LCP image. It has `fetchpriority="high"`, isn't lazy loaded and has an 800px `srcset` size for mobile. Add a `<link rel="preload">` for it.
- **Other images:** all use `loading="lazy"`. Add real `width`/`height` once the final image sizes are known.
- **Motion:** no parallax or `background-attachment: fixed`.
- **FAQ:** uses native `<details>`, so answers are in the HTML and open instantly with no JS.
- **Interactive elements:**
  - Tabs use `role="tablist"`, `role="tab"` and `aria-selected`.
  - The size / vehicle toggle uses `role="radiogroup"`.
  - The mobile menu and the call sheet close with Escape.
